## What was built

Two new modules, both read-only against everything that already existed — no modification to `.53`'s own file, no modification to the MEXC core, no modification to the risk model:

- **`aura_v05354_alpaca_equity_fill_reconciliation.py`** — the one genuinely missing piece. `.38`'s own `observe_and_reconcile_alpaca_equity_execution()` was an explicit, disclosed placeholder (`NOT_YET_IMPLEMENTED`) because nothing in this repo ever asked the broker, after submission, whether an order actually filled — `.35.submit()` only returns the broker's status *at submission time*. `poll_order_fill()` polls `client.get_order_by_client_id()` (the same call `.35.submit()` already uses for its idempotency check) until a terminal state or a caller-supplied timeout. It never fabricates a fill: a timeout returns `TIMEOUT` (or `PARTIALLY_FILLED` if that's what was last observed), never `FILLED`; a broker exception returns `POLL_ERROR`, classified and recorded, never silently treated as any other outcome. 16 tests, all passing (immediate fill, multi-poll-until-fill, every terminal status, unrecognized-status-as-open, timeout-while-open, timeout-while-partially-filled, every-poll-fails, transient-error-recovery, input validation).

- **`aura_v05355_stage1_paper_trading_runner.py`** — the Stage 1 wiring layer itself. `run_stage1a_dry_run()` and `run_stage1b_paper_cycle()` both build `.53.SymbolCycleInput`s from caller-supplied synthetic/frozen evidence and call `.53.run_cycle()` unmodified. What this module actually adds:
  - `build_enforcement_check_fn()` — bridges `.44`'s real `evaluate_hypothetical_trade()` to `.53`'s expected `enforcement_check_fn(symbol, direction, quantity, decision) -> .allowed/.reasons` contract, building a hypothetical `.43.PositionRecord` per candidate (`notional_basis="ENTRY_PRICE_ESTIMATE"`, using a caller-required `reference_price_fn`) and recording the full `EnforcementDecision` per symbol for the audit trail. This is the genuinely new integration: `.53`'s own test suite only ever exercises `enforcement_check_fn` with hand-rolled allow/block stand-ins, never the real `.44` engine — this is the first place the real one is wired in.
  - `build_shortability_audit()` — your explicit instruction: record the broker's RAW `shortable`/`easy_to_borrow` fields and the adapter's TRANSLATED `direction_capability` decision side by side in every audit record, never assuming the translation is correct. The actual fail-closed blocking behavior (refusing to submit a short unless `.34` classifies it `BORROW_CONFIRMED`) was already fully built in `.35`/`.34`/`.36`/`.38` before this milestone — this module does not duplicate that logic, only makes it independently auditable.
  - `fetch_real_alpaca_asset()` — a thin, fail-closed wrapper on `.35.fetch_asset_metadata()`. A failed fetch excludes that symbol from the cycle entirely (never a permissive empty-dict fallback) and is recorded as its own audit row.
  - `build_audit_record()` — one row per symbol per cycle covering every field in your Stage 1B checklist: timestamp, symbol, strategy id/version, signal (decision outcome + rank score), decision hash, risk decision (`.44`'s overall verdict + which dimensions blocked, or `NOT_EVALUATED` when no actionable signal was produced), intended quantity/notional, broker order ID, submission status, fill status, fill price, an explicit fees/costs disclosure (no fee model exists — see below), resulting position (from a post-cycle `.43` portfolio snapshot), kill-switch state, and the raw/translated shortability pair.

23 new tests total (16 for `.54`, 20 for `.55` — some overlap in what they exercise but each targets a distinct scenario), all passing.

## Your three decisions, as implemented

1. **LLM client stays stubbed.** `.55` never imports or references `.49`. Both Stage 1A and Stage 1B tests use `.54`'s real `NeutralDeterministicLLMClient` directly, passed in by the caller via `decide_kwargs["llm_client"]` — `.55` itself is LLM-client-agnostic and would work unmodified with a real `.49` client later.
2. **Shorts exercised, submission gated on positive verification.** Both Stage 1A and Stage 1B tests cover a verified-shortable short (reaches `READY_FOR_SUBMISSION` / actually submits) and an unverified short (`shortable=False`/`easy_to_borrow=False` and the `UNKNOWN`/missing-data case) — both blocked before ever reaching `.35.submit()`, confirmed by `client.submit_calls == []` in the test assertions. This fail-closed behavior is `.34`/`.35`'s own pre-existing logic; `.55` only adds the audit visibility.
3. **No `.51`/`.52` parameters invented.** `.55` never imports `.51`/`.52`. `SymbolRequest.technical_regime`/`short_technical_regime` exist only because `.53`'s own `SymbolCycleInput` has them (for a future Stage 1C); every test drives `sentiment_regime` synthetic evidence instead, exactly as agreed.

## Things I'm flagging rather than deciding

- **`DECIDE_KWARGS_BASE` reuse.** The decision-engine weights/threshold/penalties used throughout Stage 1A/1B tests (`sentiment_weight=1.0, wave_weight=1.0, technical_weight=0.0, short_technical_weight=0.0, decision_threshold=0.1, ai_penalty_per_concern=0.2, critic_penalty_per_issue=0.15`) are copied verbatim from `.53`'s own test fixture, not newly chosen by me. They're a reasonable, already-precedented test configuration, not a validated production setting — worth an explicit decision from you before Stage 1B runs against a real account, even in a synthetic-evidence mode.
- **`PortfolioLimits()` all-unconfigured is `.55`'s own default when a caller passes `limits=None`.** This isn't `.55` inventing a number — an all-`None` `PortfolioLimits` is `.44`'s own disclosed "not configured" state (every dimension reports `LIMIT_NOT_CONFIGURED`, not a silent pass), and the snapshot-freshness/data-quality checks still run and can still block. But it does mean Stage 1B, run this way, enforces no actual portfolio-wide numeric limit — only you can supply real ones.
- **Two independent kill switches, and two independent authorization gates, all default to blocking.** `.38`'s own supervisor kill switch defaults `True`; `.36`'s own `auth_config["kill_switch"]` also defaults `True`, and its `execution_authorized`/`paper_execution_authorized` both default `False`. `run_stage1b_paper_cycle` does not open any of these for you — `supervision_kwargs["supervisor_config"]` and `["auth_config"]` are required parameters, so opening them is a conscious choice made at call time, not a default I chose. `run_stage1a_dry_run` *does* open them by default, but only because it hardcodes `attempt_submission=False` — a blocked preview would prove nothing about the plumbing, and it can never reach `.35.submit()` regardless of these settings.
- **Credential-naming ambiguity, still unresolved.** `.env.example` now documents this explicitly (see diff): `.35`'s own `main()` reads `ALPACA_PAPER_API_KEY`/`ALPACA_PAPER_SECRET_KEY` for the equity path, but the file's own header documents that same pair as the crypto account's keys. This doesn't block `.55` (every function takes an already-constructed client, never reads an env var itself), but it does block writing a real credential-loading entry point for Stage 1B. I've added placeholder `ALPACA_EQUITY_PAPER_API_KEY`/`SECRET_KEY` entries, commented out, pending your answer on whether the equity path should get its own named pair.
- **Fees/costs.** No fee, commission, or slippage model exists anywhere in this milestone. Every audit record carries a fixed, honest disclosure string to that effect rather than a fabricated number — Stage 1B paper fills should not be read as cost-inclusive.
- **`.53`'s own `main()` is untouched**, still deliberately `NOT_WIRED`. `.55` is a separate, new entry point; a future Stage 1C (or later) may decide to wire `.53`'s CLI directly, but that wasn't asked for here and I didn't do it as a side effect.

## What Stage 1A and Stage 1B actually do

**`run_stage1a_dry_run`** — never touches a broker. Builds `.53.SymbolCycleInput`s from your synthetic evidence, calls `run_cycle(attempt_submission=False)`. Proven to reach `.38`'s real `READY_FOR_SUBMISSION`/`CONSTRUCTION_ONLY` preview for both a long and a verified-short candidate, and to be correctly blocked for an unverified short or an explicitly-engaged kill switch — all without a real Alpaca client of any kind.

**`run_stage1b_paper_cycle`** — takes a real (or, in tests, fake) Alpaca client. For each requested symbol: fetches real asset metadata (fail-closed on a failed fetch), derives `already_held` from a real `.43` portfolio snapshot, evaluates the real `.44` enforcement check, calls `run_cycle(attempt_submission=True, ...)`, polls `.54` for a fill on anything that reached submission, and logs a full audit record including the post-cycle resulting position. Tests confirm: a long buy fills and reconciles; a verified short submits; an unverified short never reaches `.35.submit()`; a portfolio-limit breach blocks before submission with the real `.44` reasons attached; a broker submission exception is recorded as `EXECUTION_UNCERTAIN` and the subsequent fill-poll honestly reports `POLL_ERROR` rather than guessing; and re-running the identical cycle a second time is correctly rejected as a duplicate at the authorization-replay layer, with `.35.submit()` never called a second time.
